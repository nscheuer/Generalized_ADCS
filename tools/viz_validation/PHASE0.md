# Phase 0-V: prototype findings and engine decision

**Decision: go with Godot 4.7 (stock build, GDScript).** Every test passes on
the development machine. One assumption from the plan was wrong and changes the
viewer design: a single camera frustum cannot cover the scene (see finding 1).
Its fix, scaled space, is now built and tested in the prototype. None of the
switch-to-Panda3D criteria were met.

Measured table: [PHASE0_results.md](PHASE0_results.md), regenerated by
`python tools/viz_validation/run_phase0.py`. Raw data goes to
`results/latest.json` (not committed).

## Setup

- Intel Arc 140V (integrated, Lunar Lake), Vulkan 1.4, Godot 4.7.2-stable
  (official build, SHA-512 verified), Forward+ renderer.
- The viewer runs as a native Windows process and is started from WSL2. Python
  in WSL serves data over the real stream protocol (`ADCS.viz.VizServer`) on
  `127.0.0.1`.
- Test data: a synthetic 7000 km, 51.6° orbit, with Sun, Moon and Earth
  orientation from DE421 via `derive_environment` (the same code validated
  against JPL Horizons in Phase 1).
- Pass/fail is decided in Python against independently computed values. Where
  possible the viewer is never checked against itself; for example, landmark
  camera positions come from Python's Earth orientation, not the viewer's.

## Findings

1. **A single frustum fails beyond far/near ≈ 1e7** (risk R1). Godot 4.7 builds
   the projection in float32. Once far/near passes about 1e7,
   (far + near)/(far − near) rounds to 1 and every depth collapses, so geometry
   disappears entirely. Measured: visible at 1e7, gone at 1e8, independent of the
   absolute near value. Godot 4.7 exposes no custom projection matrix
   (`Camera3D` offers only perspective, orthogonal and frustum modes), so an
   infinite reverse-Z projection can't be set by hand. The plan's
   "near 1 cm, far 5e8 m" frustum (ratio 5e10) would render nothing.

   **Fix, built and tested (scaled space):**
   - The frustum is adaptive: near = 0.2 × the distance to the spacecraft,
     clamped to 1 cm–100 m, and far = near × 1e6.
   - Far bodies (Earth, Moon, stars, and the spacecraft when far away) are drawn
     scaled about the camera, at a log-compressed distance inside that range.
     Scaling about the camera leaves the image unchanged.
   - The compression is monotonic, so depth order is preserved.
   - Verified: depth precision at 1 m–4e8 m with separations of 1e-5 × distance,
     and occlusion across the split (Earth hides Moon, craft hides Earth, Earth
     hides craft, Moon visible). Jitter is still zero.
   - Consequence for Phase 5/6: shaders for far bodies must work in object space
     (Earth's already does). The atmosphere ports must take the scale factor into
     account for any world-space distances.

2. **Precision holds with float64 camera-relative positions on stock float32
   Godot.** The fiducial didn't move by a measurable amount: 0.000 px RMS over
   600 frames at 1 m from a craft moving at 7.5 km/s. Feeding absolute float32
   ECI coordinates instead lost the fiducial in 564 of 600 frames. No
   double-precision engine build is needed.

3. **Earth orientation and the day/night line are right, end to end.**
   - The viewer's sub-solar point matches Python to 2e-13°.
   - In the rendered image the terminator sits 0.13 px (0.028°) from where it
     should be.
   - The float32 Earth basis agrees with the float64 math to 9e-7°.
   - Four landmarks (including Honolulu, which checks the longitude sign) land
     within 0.17 px of screen center, ≤ 2.2 km on the ground.

4. **HDR headroom: yes.** Unshaded `ALBEDO` values of 2e4–5e4 reach tonemapping
   intact (within 0.8%), so physical radiance units work. Unshaded materials
   ignore `EMISSION`.

5. **Deterministic capture: yes.** Two `--write-movie --fixed-fps 60` runs gave
   121 bit-identical frames, with time taken from the frame index.

6. **Transport.**
   - Broadcast: 10,000 rows of 512 B at 1 kHz from WSL to Windows, all received,
     no gaps, none dropped.
   - Lockstep: all 2000 rows; round trip p50 1.8 ms, p99 5.8–6.9 ms across runs,
     so estimated one-way p99 ≈ 2.9–3.4 ms (Windows and WSL clocks aren't shared,
     so one-way = round trip / 2). Occasional round-trip spikes of 45–95 ms
     (Windows scheduling, WSL relay) only slow lockstep.

7. **Frame time (GPU, Arc 140V, glow + AgX, 100k-triangle model):**
   - 1080p: p50 2.6 ms, p99 3.3 ms.
   - 1440p: p50 5.3 ms, p99 6.3 ms.

   This scene is lighter than the final one (no atmosphere, clouds or textures
   at full resolution), so treat these as a floor. On this integrated GPU, 1080p
   already fits the reference budget; 1440p fits 144 fps but not the RTX 3060
   budget. The RTX 3060 numbers still need a machine with that card.

## Bugs found by the prototype (fixed)

- **GDScript packed arrays are values.** `(dict[k] as PackedFloat64Array).append_array(x)`
  appends to a temporary copy. The frame store stayed empty until values were
  written back. Phase 5 code must follow the same pattern.
- **Messages lost after HELLO.** The GDScript client dropped messages that arrived
  in the same TCP read as HELLO: the first ROW in lockstep (already
  acknowledged), and possibly the first BLOCK in playback. It now keeps and
  returns them. The Python reference client reads one frame at a time and never
  had this bug.
- **Silent hang on compile errors.** A script that fails to compile leaves Godot
  idling in an empty window. The runner now kills Godot on timeout and reports
  its error lines.

## Not covered (still open)

- WSLg / Compatibility-renderer run, and whether lavapipe under xvfb works for CI

## Changes to the plan

- Phase 5 viewer: scaled space and the adaptive frustum are part of the core
  design (`origin.gd`), carried over from `viewer_proto/src/scene.gd`.
  Relative-to-eye polylines for orbits must use the same per-frame frustum.
- Risk R1 is resolved by scaled space (not the earlier "Moon/Sun only" fallback).
- The GDScript client in `viewer_proto/src/viz_stream.gd` is the starting point
  for `viewer/src/io/`.
